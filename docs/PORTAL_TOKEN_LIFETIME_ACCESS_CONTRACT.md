# Portal Token — Final Canonical Contract

## 1. Core invariant

**1 TOKEN = 1 USER.**

A token generated by Owner starts unassigned and can be attempted by any member. The first successful redemption locks the token to that user. A second user must be rejected. A redeemed token never becomes available again.

## 2. Two independent clocks

| Concept | Rule |
|---|---|
| Redemption window | `created_at + 24 hours` |
| User access | `15_days`, `30_days`, or `permanent`, calculated from successful redemption |

The 24-hour window is **not** the user access lifetime.

## 3. Lifecycle

`AVAILABLE` → first successful redeem → `ASSIGNED/USED`

`AVAILABLE` + 24 hours without redemption → `EXPIRED`

`AVAILABLE` → Owner revoke → `REVOKED`

`ASSIGNED/USED` → Owner revoke → `REVOKED` and portal access denied

A used/assigned token cannot return to `AVAILABLE`, including after the user's access expires.

## 4. Canonical timestamps

Token table:
- `created_at`
- `redemption_expires_at = created_at + 24 hours`
- `assigned_user_id` (NULL until successful redemption)
- `used_at` / redemption time
- `duration_mode` = `15_days | 30_days | permanent`

Grant table:
- `token_id`
- `user_id`
- `granted_at` / redemption time
- `access_expires_at` = redemption + 15/30 days, or NULL for permanent

Legacy `expires_at` fields remain only as compatibility mirrors for old data; runtime authorization uses the canonical fields above.

## 5. Concurrency

`portal_verify_token()` locks the token row with `FOR UPDATE`, validates that the token is still available, then writes `assigned_user_id`, `used_at`, and `status='used'` in the same transaction. Concurrent redemption attempts therefore have a single winner.

## 6. Member login

Authenticated members with an active assignment go directly into the portal. Logout does not remove the assignment. When access expires, the portal API denies access and the frontend watchdog signs the member out and redirects to the token gate. The account and password remain valid.

## 7. Owner

Owner access is independent of portal tokens. Owner can generate any number of tokens and never enters the member token gate.
